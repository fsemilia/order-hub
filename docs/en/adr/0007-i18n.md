# 0007 — Three UI languages with a cookie-selected root segment

🌐 **English** · [Português](../../pt-BR/adr/0007-i18n.md) · [Italiano](../../it/adr/0007-i18n.md)

- **Status:** accepted
- **Date:** 2026-11-09

## Context

The interface must be available in English (default), Portuguese and Italian. It is an
authenticated dashboard: no SEO, and URLs like `/customers` are already used in links, redirects
and tests. Cache Components must keep prerendering a static shell.

## Decision

- All pages live under `app/[locale]` (root layout, `generateStaticParams` for the three locales),
  as in the Next.js internationalization guide, so each language has its own prerendered shell.
- URLs stay **unprefixed**: `proxy.ts` rewrites `/customers` to `/<locale>/customers` from the
  `oh_locale` cookie (default `en`). `/it/...` sets the cookie once and redirects, so a link can
  still choose the language.
- Typed dictionaries in `lib/i18n/dictionaries` (English is the source type, a missing key fails
  the typecheck; a unit test checks keys and placeholders). Server Components use
  `next/root-params`; Client Components get the dictionary from a provider; Server Actions read
  the cookie (root params are not available there).
- Numbers, money and dates use `Intl` with the UI locale and the **store** currency.
- The agent's system prompt is in English and a separate block tells it the answer language.
- No i18n library: three languages and a few hundred strings do not justify one.

## Consequences

- (+) No link or redirect changed; the static shell is prerendered for each language.
- (+) Wrong translations are caught early (types + test), not in production.
- (−) Changing language reloads the page; the language is not in the URL:
  [limitations.md](../limitations.md), items U2 and U4.
